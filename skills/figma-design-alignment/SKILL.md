# 對齊 Figma 設計稿

客戶說「畫面跟設計稿不一樣」時，真正的難處不是改 CSS，而是三件事：

1. **目測會騙人**。差 12px 的卡片寬度、偏移 100px 的文字，肉眼都說「差不多」。
2. **設計稿會變**。設計師改了稿，客戶拿新稿說你做錯了，你沒有當時的證據。
3. **設計稿會自相矛盾**。同一個功能兩份稿寫不同文案，你照哪份做都會被說錯。

這個技能的價值在於：用量測取代目測、把當下的設計稿存下來、把矛盾攤開來讓客戶決定。

## 核心原則

**畫面必須與設計稿一致。** 任何刻意不一致的地方，都要寫進文件並說明原因——
沒寫進文件的偏差，日後就是「你做錯了」。

**有疑問就問使用者，不要自己決定。** 設計稿矛盾、規格衝突、文案有兩種寫法時，
你的判斷可能是對的，但決定權不在你。把選項和影響講清楚，讓使用者選。
唯一例外是純技術實作細節（用 flex 還是 grid），那不影響外觀。

## 工作流程

### 1. 取得設計稿

先試 Figma MCP（`mcp__Figma__get_figma_data`）。它能讀出**精確的規格值**——
顏色、間距、字級、字重——比從圖片量更可靠。

MCP 失敗時（額度用盡、無權限、無 MCP），請使用者截圖。要講清楚需要哪些畫面：
每個狀態都要（空白、填寫中、錯誤、成功、停用），漏了狀態就會漏掉該狀態的樣式。

> Figma 的額度限制綁**帳號**不綁 token。回 429 時換 token 沒用，
> 要換一個有付費 seat 的帳號，或等額度重置（retry-after 可能長達 60+ 小時）。
> 遇到就直接告訴使用者這個事實，別讓他白花時間換 token。

### 2. 存證（在動手改之前）

把設計稿存進 `docs/design/figma/`，檔名要能看出是哪個畫面哪個狀態
（`reg-02-form-empty.png`、`sso-05-otp-error-wrong.png`）。

這一步不能省。設計師改稿之後，這批圖是你唯一能證明「當時依據的是這一版」的東西。
同時建 `docs/design/設計稿存證.md` 做索引，標明來源與日期。

### 3. 判定畫布倍率 ⚠️ 最容易出錯的一步

設計稿的像素值**不能直接當 CSS 值**。設計師常在放大的畫布上作業——
585px 寬的稿可能對應 390px 的手機框（1.5×），2000px 的稿可能是桌機 1×。

判定方法：量一個已知元件回推倍率。例如白卡在稿上量到 525px，
若 Figma API 或既有實作顯示應為 350px，倍率就是 525÷350 = 1.5。

**算出倍率後告訴使用者你的推算依據**，再繼續。推錯的話整批尺寸都會錯，
而且錯得很一致、看起來很合理——這種錯最難發現。

同一批設計稿可能混用不同倍率（表單頁 1.5×、桌機登入頁 1×），逐份確認。

### 4. 量測比對

`scripts/measure_design.py` 掃描設計稿像素找元件邊界。用法見 `references/measuring.md`。

量到的每個值除以倍率，才是目標 CSS 值。

要比對的不只尺寸：**文案逐字、字級、字重、顏色、間距、圖示、元件狀態**都要。
文案差一個字（「不透漏」vs「不願透漏」）客戶一眼就看到。

### 5. 圖示交給使用者匯出

圖示不要自己畫近似版本。畫得再像都會有差，而且無法舉證。

在 `frontend/public/assets/icons/`（或專案對應位置）建好檔案，每個檔首行註明用途、
尺寸、顏色，然後**告訴使用者路徑，請他從 Figma 匯出後貼上**。

收到後檢查：**數一下 `<path>` 數量**。匯出時常漏選內層圖層，
結果只有外圈的圓、沒有裡面的驚嘆號或打勾。發現了就請使用者重匯。

一個例外：深色按鈕上的白色轉圈之類的元素，若匯出檔把顏色寫死會看不見，
保留 `currentColor` 的 inline SVG，並在註解說明為什麼。

### 6. 改完必須重新量測驗證

改完就宣告完成是這個流程最常見的失敗。改完之後：

用 Playwright 開實際畫面，`getBoundingClientRect()` 量出實際值，
與設計稿換算值逐項比對。**目測「看起來對了」不算驗證過。**

視窗尺寸要對應設計稿（手機版 390×844、桌機版依設計稿畫布）。

### 7. 截圖與報告

每個狀態截一張圖存 `docs/design/screenshots/`，寫成對照報告
（見 `references/doc-templates.md`）。報告要讓使用者**快速確認**，所以：

- 修正項目用表格：項目｜設計稿｜修正前｜修正後
- 每張截圖標明「🖥️ 實際畫面」與對照的設計稿檔名——
  否則使用者分不出哪張是設計稿、哪張是你做的
- 截圖尺寸統一，且**不要用 fullPage**：`position: fixed` 的元素在全頁截圖裡
  會被合成在視窗位置，看起來像浮在頁面中間，造成誤判

### 8. 記錄矛盾與例外

兩份文件，用途不同：

**設計稿矛盾清單** — 設計稿自己打架的地方。列出各版本說法、採用哪個、為什麼。
這是客戶質疑時的擋箭牌：不是實作錯，是設計稿本身沒有單一答案。
發現矛盾時**先問使用者要用哪個**，不要自己選。

**刻意不一致的例外** — 明知與設計稿不同但仍這樣做的地方，寫清楚原因。
例如設計稿沒有的欄位（但後端需要）、設計稿可點但功能未完成所以停用的按鈕。

## 產出結構

```
docs/design/
├── README.md              # 各檔用途、畫布倍率換算表
├── FIGMA.md               # Figma 連結＋API 讀出的規格值
├── 設計稿存證.md           # 設計稿原圖索引（來源、日期）
├── 設計稿矛盾清單.md        # 矛盾＋採用理由；刻意例外
├── 畫面對照_<功能>.md       # 修正表＋實際畫面截圖
├── figma/                 # 設計稿原圖（存證）
└── screenshots/           # 實作後的實際畫面
```

專案已有其他文件慣例時，先問使用者要放哪裡。

## 常見錯誤

這些都是實際踩過的坑：

**把放大稿的像素值直接當 CSS 值** — 做出來大 1.5 倍，但每個元件都一致地大，
看起來很合理。務必先判定倍率。

**改完沒重新量** — 改的時候算對了，改完沒驗證，實際渲染出來又是另一回事
（padding 疊加、flex 壓縮）。

**用 justify-between 實作「左右分開」** — 設計稿上文字是**置中對齊某個元件**、
另一個元素靠右，不是兩端對齊。量一下兩者的中心點就知道差別。

**全頁截圖造成的假象** — fixed 元素在 fullPage 截圖裡位置錯亂，
會讓人以為版面壞了。用視窗截圖。

**沿用既有 token 而不看實際色值** — 設計稿的 `#718096` 和專案的 `#5B6878`
都是「灰色文字」，但不是同一個。逐欄取色，不同就新增 token。

**假設元件庫與實際頁面一致** — 兩者可能矛盾（元件庫寫「不願透漏」、
頁面寫「不透漏」）。以實際頁面為主，但要問使用者確認。
