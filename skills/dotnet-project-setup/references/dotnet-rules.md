# .NET Development & Testing Specifications

## 🧱 Backend Core Isolation

> Architecture: **DDD + Clean Architecture + CQRS**. Dependency direction: `Domain` ← `Application` ← `Infrastructure` / `WebApi`; `Persistence` → `Application` and `Persistence` → `Domain` (implements both `IUnitOfWork` and `IRepository<T>` from Domain). The CQRS core (interfaces, dispatchers, `AddCqrs`) lives in `Application/Cqrs/CQRS.cs` (namespace `<ProjectName>.Application.Cqrs`).

- 📂 **Layer Responsibilities**:
  - `Domain` — Pure domain model: Entities, Aggregate Roots, Value Objects, Domain Services, Domain Events. Defines `IRepository<T>`, `IUnitOfWork`, `IDomainEventDispatcher`, and `IDomainEventHandler<TEvent>` interfaces. **Zero framework dependencies** — no EF Core attributes, no FluentValidation, no HTTP libraries.
  - `Application` — Use cases: command/query handlers, validators, mappers, domain event handlers, and application-level orchestration. References `Domain` only. Orchestrates domain objects without containing business rules. Domain abstractions (`IRepository<T>`, `IUnitOfWork`, domain event interfaces, and any interface required by Domain Managers) live in `Domain`. Read-side abstractions (`IXxxReadRepository`, returning DTOs for QueryHandlers) live in `Application/Interfaces/` — they return DTOs, which `Domain` must not know about — and are implemented in `Persistence`. The **CQRS core infrastructure** (ICommand/IQuery/IHandler interfaces, Dispatcher implementations, `AddCqrs` DI extension) lives in `Cqrs/CQRS.cs` (namespace `<ProjectName>.Application.Cqrs`) and depends on `Microsoft.Extensions.DependencyInjection.Abstractions`. That file contains **no business logic**; keep commands/queries/handlers in the `Commands/`/`Queries/`/`EventHandlers/` folders.
  - `Infrastructure` — External integrations: email, storage, message queues, external HTTP clients. Implements Domain-defined interfaces when the capability is required by Domain Services; implements Application-defined interfaces only for application-only orchestration concerns.
  - `Persistence` — Persistence implementations: EF Core DbContext, Dapper/raw SQL access, repositories, read repositories, and Unit of Work. Implements `IRepository<T>` and `IUnitOfWork` from `Domain`, and `IXxxReadRepository` from `Application`. **`DbContext` types never leave this project** — `Application` cannot reference them, so every handler goes through one of those interfaces. Do not create Persistence-local interfaces for internal plumbing.
  - `WebApi` — Entry point: Minimal API endpoints, middleware. References `Application` (dispatcher injection, `AddCqrs` registration — the CQRS core is part of Application).
- 🔢 **Enum Backing Type**: Any enumerable property — including but not limited to `Status`, `Type`, `State`, `Role`, `Category`, `Kind` — **must** be declared as `enum : byte`. Example: `public enum OrderStatus : byte { Pending = 0, Processing = 1, Completed = 2, Cancelled = 3 }`.
- 🧬 **Domain Model Style** (decided at project setup — ask the user):
  - **Rich Domain Model** *(Recommended for complex domains)* — Entities encapsulate behaviour and enforce invariants. Business rules live inside domain objects (e.g., `Order.AddItem()`, `Order.Cancel()`). Entities must use private/protected setters; creation goes through factory methods or static constructors — no public parameterless constructors on aggregates. Application handlers remain thin orchestrators. Domain events are raised inside aggregates and dispatched after transaction commit.
  - **Anemic Domain Model** — Entities are pure POCOs with public setters. All business logic and orchestration lives in Application-layer command handlers. Acceptable for simple CRUD-heavy services. Domain Services in `Domain/DomainServices/` **must be named `XxxManager`** (e.g., `OrderManager`, `PricingManager`) — never `XxxService`, which is reserved for Application/Infrastructure layer classes.
- 🏛️ **DDD Building Blocks** (enforce when Rich Domain Model is chosen; optional for Anemic):
  - **Aggregate Root**: Every aggregate has a single Aggregate Root that controls all access. External code must only interact through the root. Aggregates enforce their own invariants.
  - **Value Objects**: Immutable; equality is structural, not identity-based. Implement as `record` types in `Domain/ValueObjects/`.
  - **Domain Events**: Defined in `Domain/Events/`. Published via `IDomainEventDispatcher` (defined in `Domain/Interfaces/`) and handled by Application-layer event handlers in `Application/EventHandlers/` — always after the persistence transaction commits successfully.
    - **Rich Domain Model**: Events are queued inside aggregates via `AddDomainEvent()`; `IUnitOfWork.CommitAsync()` collects events, commits persistence, then dispatches them after successful commit.
    - **Anemic Domain Model**: Application orchestration or `XxxManager` dispatches explicit in-process events only after `IUnitOfWork.CommitAsync()` succeeds.
  - **Domain Services**: Used for operations that span multiple aggregates or logic that does not belong to a single entity. Placed in `Domain/DomainServices/`. No HTTP calls.
    - **Rich Domain Model**: pure domain logic only — no direct persistence calls and no repository injection. Application handlers load required aggregates/references and pass them into domain methods/services.
    - **Anemic Domain Model**: named `XxxManager`. May inject only interfaces defined in `Domain/Interfaces/` (for example `IRepository<T>` or custom domain capability interfaces) to read/write entities or coordinate domain workflows. Transaction boundaries are still managed by the Application layer handler via `IUnitOfWork`.
  - **Repository Abstraction**: `IRepository<T>` is defined in `Domain/Interfaces/`. Repositories operate at the aggregate boundary — never expose `IQueryable<T>` outside `Persistence`. Rich Domain Services do not inject repositories; Anemic `XxxManager` classes may inject Domain-defined repositories and Domain-defined capability interfaces only.
  - **Read Repository Abstraction**: `IXxxReadRepository` is defined in `Application/Interfaces/` and implemented in `Persistence/ReadRepositories/`. It serves QueryHandlers only, returns DTOs/projections rather than aggregates, and never exposes `IQueryable<T>`. It does **not** perform writes and is never injected into a CommandHandler or a Domain Manager — a CommandHandler that needs to read does so through the write-side repository, since its reads must come from the write connection and must be tracked. Conversely, QueryHandlers do not inject `IRepository<T>`: loading a whole aggregate to render a screen over-fetches and drags in navigation properties the view does not need.
    - **Anemic model**: this boundary matters more, not less. Without aggregate roots there is nothing to naturally limit how many repositories a CommandHandler or `XxxManager` touches, so a write-path component reading four tables is routine. Every one of those reads goes through the Domain-defined write-side repository — placing `IXxxReadRepository` in `Application/Interfaces/` is what makes this enforceable, since `XxxManager` may only inject interfaces from `Domain/Interfaces/` and therefore cannot reach a read repository at all.
- 🌐 **Timezone & Time Abstraction**: 📢 **[MANDATORY]** Before running DB migrations or designing schemas, explicitly ask the user for the targeted database timezone. Any expiration/time logic must use **`TimeProvider`** instead of direct system clock calls.

## 🔌 Environment Isolation & Test Backdoors
- 🔌 **Service Toggle**: External services (Email, Storage, Queues) must be interface-driven. In Dev/Test envs, they must default to `LocalFileStorage`, `MockEmailSender` (logs only), or In-Memory Queues.
- 🔐 **OTP & Auth Bypass**: Dev/Test environments may support a `FixedOTP` config (e.g., "123456") and a testing header (e.g., `X-Test-User-Id`) when automated tests need to bypass interactive authentication. These backdoors must be disabled in production.

## ⚙️ Environment & Architecture
- 💻 **SDK**: Implement using **.NET 10**. Solutions must use the modern `*.slnx` format. Central Package Management (CPM) via `Directory.Build.props` and `Directory.Packages.props` is mandatory.
- 📦 **Package Versions**: Always use the **latest stable** version available at scaffold time. Never rely on version numbers stored in this document or from memory — look up the current release on NuGet.org before adding any package. Preview, beta, and RC releases are strictly forbidden.
- 📜 **Package Licensing**: Only **MIT- or Apache-2.0-licensed** packages are permitted. GPL/copyleft-licensed packages are forbidden — they impose obligations incompatible with typical closed-source backends.
- 🔐 **Secrets**: Never hardcode secrets (connection strings, API keys, tokens). Use environment variables or a secret manager for every secret. `.gitignore` must exclude local env files, secrets, and build output.
- 📄 **One Class Per File**: Each class must reside in its own dedicated file. The only exception is auxiliary types (request, response, record, model, DTO) that exclusively serve a single primary class — those may be co-located in the same file as that primary class.
- 🎨 **Code Style Consistency**: All code across the entire solution **must** adhere to a single, unified code style standard. Establish an `.editorconfig` file at the solution root that enforces naming conventions (PascalCase for public members, camelCase for parameters/locals), indentation (4 spaces), line length limits, and brace placement. Run `dotnet format` as part of the CI/CD pipeline to enforce consistency. No inconsistent naming patterns, formatting, or structural conventions are permitted across projects or layers.
- ✒️ **Constructors**: All classes requiring DI **must strictly use .NET 10 Primary Constructors**. Explicit boilerplate constructor blocks and manual `private readonly` backing fields are prohibited.
- 🌐 **Web Framework**: Use Minimal APIs. Upon endpoint creation, explicitly ask the user if they want to integrate `FastEndpoints` and provide a concise architectural comparison (Route Groups vs FastEndpoints).
- 💾 **Data Access**: Default to **EF Core + Dapper/raw SQL** in the `Persistence` project, but keep `Domain` and `Application` persistence-agnostic. EF Core is the default for aggregate persistence and transactional commands; **Dapper/raw SQL** handles complex/reporting queries and narrowly scoped performance-sensitive updates. The DB provider is decided at project setup — **default to SQL Server, then PostgreSQL**; do not use SQLite. Ask the user before scaffolding.
  - **GUID/UUID Strategy**: When using GUID as primary key or unique identifier in database tables, **MUST always use UUID V7**. UUID V7 provides sequential ordering by timestamp, improving database index performance and query efficiency compared to V4 random GUIDs. Configure EF Core to generate UUID V7 values via `ValueGeneratedOnAdd()` with the appropriate `HasDefaultValueSql()` for the target database (e.g., a UUID V7 wrapper on SQL Server; `gen_random_uuid()` for PostgreSQL with the pgcrypto extension). Note SQL Server's built-in `NEWID()` is random, not V7, and `NEWSEQUENTIALID()` is not time-ordered the same way — prefer generating V7 in application code or a dedicated SQL function when the provider lacks native V7.
  - **Raw SQL update policy**: Repositories may use raw SQL/Dapper `UPDATE` only as a Persistence-layer optimization for batch updates, performance-sensitive narrow updates, counters, flags, or state changes that do not bypass aggregate invariants and do not require domain events. Do not use raw SQL to silently perform core business transitions such as order cancellation, payment completion, inventory deduction, or any operation that requires a domain method, invariant enforcement, or domain event. If a bulk operation requires auditing, explicitly write audit records in the same transaction or load aggregates and invoke domain behavior.
  - **Unit of Work** — `IUnitOfWork` is defined in `Domain/Interfaces/` and implemented in `Persistence/UnitOfWork/`. It is a persistence-agnostic transaction/commit boundary with `Task CommitAsync(CancellationToken)`, used by both Rich and Anemic models. Application command handlers decide when to commit. Repositories must never call `DbContext.SaveChangesAsync()`, commit SQL transactions, or expose EF/SQL transaction types to `Domain` or `Application`.
    - **Rich Domain Model**: `CommitAsync()` persists aggregate changes, commits the transaction, then dispatches collected domain events via `IDomainEventDispatcher` only after the persistence commit succeeds. Clear domain event queues after successful dispatch.
    - **Anemic Domain Model**: `CommitAsync()` commits all repository operations for the use case. Domain services/managers may orchestrate repositories but must not open transactions or commit.
    - **EF + Dapper/raw SQL**: when both are used in one command, they must share the same connection and transaction owned by `IUnitOfWork`/Persistence. For EF-backed implementations, Dapper/raw SQL repositories in `Persistence` may inject the concrete `AppUnitOfWork` to call `EnsureTransactionAsync()` and use its exposed `Connection` / `CurrentTransaction`. `AppUnitOfWork` must not be exposed to `Domain` or `Application`, and repositories must not create their own independent transactions. Enrolment requires **all three** of: (1) `await EnsureTransactionAsync()` *before* the command — otherwise `CurrentTransaction` is `null`, and a null transaction makes Dapper autocommit the statement as its own independent write (no error, silent consistency break); (2) executing on `AppUnitOfWork.Connection` (EF's own connection), never a freshly constructed one; (3) passing `transaction: AppUnitOfWork.CurrentTransaction`. Passing `CurrentTransaction` while executing on a *different* connection throws (transaction not associated with the connection) or splits the work across two independent transactions. `Connection` and `CurrentTransaction` must both derive from the same `DbContext`.
    - **DI registration**: register `AppUnitOfWork` once per scope, then map `IUnitOfWork` to that same scoped instance. Do not create Persistence-local interfaces solely to access the current transaction.
    - **Transaction mechanism**: implement the commit boundary with EF Core's own transaction API — `dbContext.Database.BeginTransactionAsync()` / `IDbContextTransaction` (as the template's `EnsureTransactionAsync()` shows). **Do NOT use `System.Transactions.TransactionScope` / ambient transactions.** Ambient scopes interact poorly with async EF, and on SQL Server a `TransactionScope` spanning more than one connection can silently escalate to a distributed (MSDTC) transaction — a reliability and portability hazard. The explicit `IUnitOfWork` boundary (one connection, one `IDbContextTransaction`, shared by EF and any raw-SQL/Dapper repository) already guarantees a single all-or-nothing commit, so `TransactionScope` adds risk without adding consistency.
  - Calling `DbContext.SaveChangesAsync()`, committing a `DbTransaction`, or directly managing transaction scope from any handler is strictly forbidden regardless of domain model style.
- 🔄 **CQRS Implementation**: Replicate the boilerplate from `references/dotnet-cqrs-template.cs` (same directory as this file) verbatim into **`<ProjectName>.Application/Cqrs/CQRS.cs`** (namespace `<ProjectName>.Application.Cqrs`) — a single file inside the Application project, **not** a standalone `Cqrs` project. It contains **only** the core infrastructure (interfaces, dispatchers, `AddCqrs` extension) — no business commands, queries, or handlers. All command/query/handler implementations live elsewhere in the same `Application` project (`Commands/`, `Queries/`, `EventHandlers/`). Manual, line-by-line registration of handlers is prohibited; you must invoke `services.AddCqrs(typeof(SomeHandler).Assembly)` in `WebApi`.
  - **Database routing** — CQRS is always present; the read/write split is not. The topology is chosen once at project setup and only one shape exists in a given codebase:
    - **Single connection** (default): every handler uses `ConnectionStrings:Default`. CommandHandlers write through repositories/`IUnitOfWork`; QueryHandlers read the same database but must still use `AsNoTracking()` for EF/LINQ reads. The routing rules below do not apply — there is nothing to route to.
    - **Read/write split** (only when read replicas were enabled at setup): `ConnectionStrings:Write` and `ConnectionStrings:Read` exist, and the rules below are binding.
  - **Write vs Read routing (read/write split only)** — the default is mechanical: **Command ⇒ Write, Query ⇒ Read**. Overrides are a closed list, not a judgement call:
    - **CommandHandlers always use Write — no exceptions.** This includes every read a command performs: validation, invariant checks, idempotency checks, aggregate loading, uniqueness checks, and read-before-write logic. Replication lag on any of these silently breaks business invariants.
    - **QueryHandlers use Read by default** — list/search/paging, reports and aggregates, master-data lookups (dropdowns), audit-trail browsing. Simple queries use EF Core + LINQ with `AsNoTracking()`; complex, reporting, or multi-join queries use Dapper/raw SQL. Both go to Read.
    - **QueryHandlers must use Write in these cases only**: (1) the query backs a page the user is redirected to immediately after a command that changed it (read-your-writes); (2) the query is a later step in one user-visible operation sequence whose earlier step wrote; (3) the value must be exact at read time — balance, stock, quota, credit limit; (4) the query decides uniqueness or existence in order to permit a subsequent write; (5) the query reads current state-machine status or distributed-lock state.
    - Anything not on that list goes to Read. "It feels safer on Write" is not a reason — routing ordinary query load to the master defeats the split entirely.
  - **How to route a query to Write**: handlers cannot inject a `DbContext` — `Application` references `Domain` only — so the mechanism lives in `Persistence`. Register a second implementation of the same `IXxxReadRepository` bound to the write context and resolve it with a keyed service (see `dotnet-scaffold.md` → CQRS Pattern); the handler still depends only on the Application-layer read interface. State the reason in a comment on the handler naming which of the five cases above applies. Never make Write the ambient default for a shared read abstraction.
  - **Persistence abstractions do not vary with topology**: `IRepository<T>`/`IXxxRepository` (write side, `Domain/Interfaces/`, returns aggregates) and `IXxxReadRepository` (read side, `Application/Interfaces/`, returns DTOs) exist in both single-connection and split deployments, and both are implemented in `Persistence`. Switching topology changes DI registration and `appsettings` only — never a handler, an interface, or a query body.
  - **DbContext separation (read/write split only)**: `DbContext` types stay inside `Persistence` and are never injected into `Application`. Scaffold a write-side context (`WriteDbContext`) on `ConnectionStrings:Write` and a `ReadDbContext` on `ConnectionStrings:Read`, both deriving from a shared abstract `AppDbContext` so the model is configured once. Write repositories and `IUnitOfWork` take `WriteDbContext`; read-repository implementations take `ReadDbContext`. EF Core migrations and the design-time factory bind to the **Write** connection only. A transaction never spans both contexts.
- 📡 **Event-Driven Design (EDD)** (decided at project setup — ask the user):
  - **Domain Events** (in-process) — raised inside aggregates, dispatched synchronously via `IDomainEventDispatcher` after `IUnitOfWork.CommitAsync()` commits persistence successfully. For decoupling non-critical in-process side effects within a single service boundary. Never dispatch before the transaction commits. In-process domain event handlers must not perform irreversible or reliability-critical side effects directly.
  - **Integration Events** (cross-service) — optional. Enable only when the project has confirmed cross-service asynchronous communication. Events are defined in `Application/IntegrationEvents/`. `IEventBus` interface lives in `Application/Interfaces/`; the broker-specific implementation lives in `Infrastructure/`.
  - Email, external API calls, cross-service notifications, and durable projections must not be performed directly in in-process domain event handlers. Prefer explicit Application orchestration for simple workflows; use retryable background work with idempotency when asynchronous processing is required.
  - Integration event consumers must be **idempotent** — processing the same event twice must produce the same outcome.
- 🪵 **Logging**: Standardize exclusively on **Serilog**. All log calls **must** use structured message templates with named placeholders — string interpolation in log messages is strictly prohibited.
  ```csharp
  // ❌ Forbidden — string interpolation destroys structure
  logger.LogInformation($"User {userId} purchased {productId} for {amount}");

  // ✅ Required — structured template with named properties
  logger.LogInformation("User {UserId} purchased {ProductId} for {Amount}", userId, productId, amount);
  // 'logger' is the Primary Constructor parameter — no _logger backing field
  ```
  - **Bootstrap logger**: `Program.cs` must configure a bootstrap `Log.Logger` before `WebApplication.CreateBuilder()` to capture startup errors. Wrap the entire host startup in `try/catch/finally` with `Log.CloseAndFlush()` in the `finally` block.
  - **Request logging**: Always call `app.UseSerilogRequestLogging(...)` with a custom `MessageTemplate` that includes `{RequestMethod}`, `{RequestPath}`, `{StatusCode}`, and `{Elapsed}`. This replaces the verbose default ASP.NET Core request logging with a single structured entry per request.
  - **Enrichers** (mandatory, add to WebApi project): `Serilog.Enrichers.Environment` (`WithMachineName`), `Serilog.Enrichers.Process` (`WithProcessId`), `Serilog.Enrichers.Thread` (`WithThreadId`). Register via `.Enrich.WithMachineName().Enrich.WithProcessId().Enrich.WithThreadId()`.
  - **Configuration**: Serilog must be fully configured via `appsettings.json` using `ReadFrom.Configuration()`. Hard-coded sink configuration in `Program.cs` is forbidden. Use `ReadFrom.Services()` to allow DI-resolved sinks.
  - **Log levels**: Production default is `Information`; override `Microsoft.*` and `System.*` to `Warning`; Development overrides to `Debug`. EF Core SQL commands: `Microsoft.EntityFrameworkCore.Database.Command` → `Information` in Development only.
  - **Sensitive data**: Never log passwords, tokens, PII, or connection strings. Destructure objects explicitly; do not log entire request/response bodies unless redacted.
- 📊 **Observability (OpenTelemetry)**: During project setup, ask the user whether to integrate **OpenTelemetry**. Recommended for production services, microservices, or any service communicating with external systems. If enabled:
  - Install `OpenTelemetry.Extensions.Hosting`, `OpenTelemetry.Instrumentation.AspNetCore`, `OpenTelemetry.Instrumentation.Http` in the `WebApi` project.
  - Ask which exporter to use: **OTLP** (Jaeger/Zipkin/Collector), **Console** (dev/debug), or **Azure Monitor**.
  - Register in `Program.cs`:
  ```csharp
  builder.Services.AddOpenTelemetry()
      .WithTracing(tracing => tracing
          .AddAspNetCoreInstrumentation()
          .AddHttpClientInstrumentation()
          .AddOtlpExporter())  // or .AddConsoleExporter() for dev
      .WithMetrics(metrics => metrics
          .AddAspNetCoreInstrumentation()
          .AddHttpClientInstrumentation()
          .AddOtlpExporter());
  ```
- 🔗 **HTTP Client & Resilience**: Any outbound HTTP call to an external Web API **must** use a named/typed `HttpClient` registered via `AddHttpClient(...)` with **`Microsoft.Extensions.Http.Resilience`**. Call `.AddStandardResilienceHandler()` on every registration — this enables the built-in defense pipeline: Rate Limiting → Timeout → Retry → Circuit Breaker. Raw `HttpClient` instantiation (`new HttpClient()`) is strictly prohibited.
  ```csharp
  services.AddHttpClient("PaymentClient", c => c.BaseAddress = new Uri(config["Payment:BaseUrl"]!))
      .AddStandardResilienceHandler(options =>
      {
          options.Retry.MaxRetryAttempts = 3;
          options.CircuitBreaker.FailureRatio = 0.5;
      });
  ```
- 📡 **API Documentation**: Use `Microsoft.AspNetCore.OpenApi` (`AddOpenApi()`) with **Scalar** (`Scalar.AspNetCore`) for API documentation UI. Do NOT use Swashbuckle or Swagger UI under any circumstance.
- 📋 **Validation**: Use **FluentValidation** for all request/command/query validation. Validators live in `Application/Validators/`. Package split: `FluentValidation` is referenced by the `Application` project; `FluentValidation.DependencyInjectionExtensions` is referenced by `WebApi` and registered via `AddValidatorsFromAssembly(typeof(SomeValidator).Assembly)`. At the endpoint layer, invoke validation using `await validator.ValidateAndThrowAsync(request, ct)` before dispatching commands/queries. Never use DataAnnotations for business rule validation — DataAnnotations are permitted only for OpenAPI metadata hints.
- 🗃️ **Caching**: Do not scaffold caching by default. If the project has a confirmed caching need, prefer **`HybridCache`** and avoid direct `IDistributedCache` / `IMemoryCache` usage in application code. `HybridCache` requires the **`Microsoft.Extensions.Caching.Hybrid`** package (it is *not* built into the shared framework) — add it and call `builder.Services.AddHybridCache()` only when caching is actually needed.
- 🗺️ **Object Mapping**: **AutoMapper is strictly prohibited — no exceptions.** Mapper classes live in `Application/Mappers/`. Choose one of the following during project setup (ask the user and provide a recommendation):
  - **Mapperly** (`Riok.Mapperly`) — Source generator; zero runtime overhead, compile-time type safety, ideal for performance-sensitive projects. **Recommended for most projects.** Add to `Application.csproj` with `<PrivateAssets>all</PrivateAssets>` to prevent the analyzer from leaking as a transitive runtime dependency.
  - **Mapster** — Runtime mapper; more flexible for dynamic/complex mapping scenarios, richer configuration API.
  - **None** — Acceptable for simple projects or where explicit manual mapping improves readability and traceability.

## 🧪 Testing Guidelines
- 🧪 **Required Test Projects**: Every scaffolded solution must include exactly these baseline test projects:
  - `tests/<ProjectName>.UnitTests/` for isolated unit tests of domain logic, validators, mappers, and application handlers.
  - `tests/<ProjectName>.IntegrationTests/` for ASP.NET Core request pipeline, DI, persistence, and infrastructure integration tests.
- 🧪 **Unit Tests**: Use **xUnit** as the test framework and **NSubstitute** for mocks. Unit tests must not use real DB, filesystem, network, or external services. Outbound HTTP calls must be stubbed or intercepted.
- 🧪 **Integration Tests**: Use **Microsoft.AspNetCore.Mvc.Testing** / `WebApplicationFactory` with a test web host. The integration test project must use the Web SDK. Integration tests must cover representative request/response flows, DI wiring, validation behavior, persistence behavior, and error responses.
- 🧪 **Coverage Standard**: Placeholder tests are not sufficient. Every generated or implemented feature must include meaningful unit and/or integration tests that verify expected behavior, failure paths, and important boundary conditions. The scaffold is not complete until `dotnet test` passes with these meaningful tests.
- 🧪 **Excluded Test Projects**: Do not scaffold any test project other than `UnitTests` and `IntegrationTests` as part of this skill. If a future project needs more test projects, treat them as a separate explicit request outside the default backend scaffold.
