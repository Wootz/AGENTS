# .NET Development & Testing Specifications

## 🧱 Backend Core Isolation

> Architecture: **Clean Architecture + CQRS**, in one of two established forms chosen at project setup — layering, dependency direction, and CQRS are identical in both; only where business logic lives differs:
> - **Anemic Domain Model** (default) — entities are data holders, business logic lives in Application handlers and, when it is genuinely shared domain logic, in capability-named Domain Services. This is Clean Architecture / Onion Architecture as practised in Microsoft's **eShopOnWeb** reference application. It is **not DDD** — it borrows DDD's layering and vocabulary without the Rich Domain Model, and the documentation must not claim otherwise.
> - **Rich Domain Model** — entities encapsulate behaviour and enforce their own invariants. This is **DDD** proper (Evans / Vernon), as in Microsoft's **eShopOnContainers** Ordering service.
>
> Both are named, widely-used architectures with published reference implementations; neither is an invention of this skill. What must not happen is a hybrid — Rich-looking entities (private setters, factory methods) whose rules actually live in handlers is neither architecture and has no reference to check against.
>
> Dependency direction: `Domain` ← `Application` ← `Infrastructure` / `Api`; `Persistence` → `Application` and `Persistence` → `Domain` (implements `IUnitOfWork`, the per-aggregate `IXxxRepository`, and `IXxxReadRepository`, wherever each is declared). The CQRS core (interfaces, dispatchers, `AddCqrs`) lives in `Application/Cqrs/CQRS.cs` (namespace `<ProjectName>.Application.Cqrs`).

- 📂 **Layer Responsibilities**:
  - `Domain` — Pure domain model: Entities, Aggregate Roots, Value Objects, Domain Services, Domain Events. Under the **Rich** model it also defines the per-aggregate `IXxxRepository` write-side interfaces, `IUnitOfWork`, `IDomainEventDispatcher`, and `IDomainEventHandler<TEvent>`; under **Anemic** those all live in `Application` instead (see *Where repository interfaces live*), leaving `Domain` as pure data. **Zero framework dependencies** either way — no EF Core attributes, no FluentValidation, no HTTP libraries.
  - `Application` — Use cases: command/query handlers, validators, mappers, domain event handlers, and application-level orchestration. References `Domain` only. Orchestrates domain objects without containing business rules. Which project owns the `IXxxRepository`, `IUnitOfWork`, and domain-event interfaces depends on the domain model style (see *Where repository interfaces live*): `Domain` under Rich, `Application` under Anemic. `IXxxReadRepository` always lives in `Application/Interfaces/` — it returns DTOs, which `Domain` must not know about. All of them are implemented in `Persistence`. The **CQRS core infrastructure** (ICommand/IQuery/IHandler interfaces, Dispatcher implementations, `AddCqrs` DI extension) lives in `Cqrs/CQRS.cs` (namespace `<ProjectName>.Application.Cqrs`) and depends on `Microsoft.Extensions.DependencyInjection.Abstractions`. That file contains **no business logic**; keep commands/queries/handlers in the `Commands/`/`Queries/`/`EventHandlers/` folders.
  - `Infrastructure` — External integrations: email, storage, message queues, external HTTP clients. Implements Domain-defined interfaces when the capability is required by Domain Services; implements Application-defined interfaces only for application-only orchestration concerns.
  - `Persistence` — Persistence implementations: the two EF Core DbContexts (`WriteDbContext`, `ReadDbContext`), Dapper/raw SQL access, repositories, read repositories, and Unit of Work. Implements the per-aggregate `IXxxRepository` interfaces, `IUnitOfWork`, and `IXxxReadRepository` — declared in `Domain` or `Application` per the domain model style (see *Where repository interfaces live*). **`DbContext` types never leave this project** — `Application` cannot reference them, so every handler goes through one of those interfaces. Do not create Persistence-local interfaces for internal plumbing.
  - `Api` — Entry point: Minimal API endpoints, middleware. References `Application` (dispatcher injection, `AddCqrs` registration — the CQRS core is part of Application).
- 🔢 **Enum Backing Type**: Any enumerable property — including but not limited to `Status`, `Type`, `State`, `Role`, `Category`, `Kind` — **must** be declared as `enum : byte`. Example: `public enum OrderStatus : byte { Pending = 0, Processing = 1, Completed = 2, Cancelled = 3 }`.
- 🧬 **Domain Model Style** (decided at project setup — ask the user):
  - **Rich Domain Model** *(Recommended for complex domains)* — Entities encapsulate behaviour and enforce invariants. Business rules live inside domain objects (e.g., `Order.AddItem()`, `Order.Cancel()`). Entities must use private/protected setters; creation goes through factory methods or static constructors — no public parameterless constructors on aggregates. Application handlers remain thin orchestrators. Domain events are raised inside aggregates and dispatched after transaction commit.
  - **Anemic Domain Model** — Entities are pure POCOs with public setters. The main business logic and orchestration live in the Application-layer command/query handlers. Only logic shared by more than one handler goes in a Domain Service under `Domain/DomainServices/`. Acceptable for simple CRUD-heavy services.
    - **Name them after the capability they provide**, not the entity they touch: `PricingService`, `InventoryAllocationService`, `CreditCheckService` — never `OrderService`. An entity-named service has no natural size limit and accumulates every operation on that entity; a capability-named one is bounded by its own name.
    - **Command and query handlers are the service layer**; a Domain Service holds only rules shared across handlers. A handler whose body is a single call into a Domain Service adds boilerplate without value — the logic belongs in the handler.
    - Disambiguate from Application/Infrastructure services by namespace and folder (`<Project>.Domain.DomainServices`), not by suffix.
- 🏛️ **DDD Building Blocks** (enforce when Rich Domain Model is chosen; optional for Anemic):
  - **Aggregate Root**: Every aggregate has a single Aggregate Root that controls all access. External code must only interact through the root. Aggregates enforce their own invariants.
  - **Value Objects**: Immutable; equality is structural, not identity-based. Implement as `record` types in `Domain/ValueObjects/`.
  - **Domain Events**: Event types are defined in `Domain/Events/`. Published via `IDomainEventDispatcher` (placed per *Where repository interfaces live*: `Domain/Interfaces/` under Rich, `Application/Interfaces/` under Anemic) and handled by Application-layer event handlers in `Application/EventHandlers/` — always after the persistence transaction commits successfully.
    - **Rich Domain Model**: Events are queued inside aggregates via `AddDomainEvent()`; `IUnitOfWork.CommitAsync()` collects events, commits persistence, then dispatches them after successful commit.
    - **Anemic Domain Model**: the Application handler dispatches explicit in-process events only after `IUnitOfWork.CommitAsync()` succeeds. Domain Services never dispatch — `IDomainEventDispatcher` lives in `Application`, which `Domain` cannot reference.
  - **Domain Services**: Used for operations that span multiple aggregates or logic that does not belong to a single entity. Placed in `Domain/DomainServices/`. No HTTP calls. **Pure domain logic only in both models** — no persistence calls and no repository injection. Application handlers load the required aggregates/entities through the write-side repository and pass them into the domain service.
    - **Rich Domain Model**: domain methods on aggregates plus pure Domain Services.
    - **Anemic Domain Model**: capability-named (see Domain Model Style above), created only when a second handler needs the same rule. Under this layout `IXxxRepository` lives in `Application`, so a Domain Service cannot see it; it may inject only custom domain capability interfaces defined in `Domain/Interfaces/` (e.g. a pricing-rule provider) — never a repository. Transaction boundaries are managed by the Application handler via `IUnitOfWork`.
  - **Where repository interfaces live** — this follows the **domain model style**, because the caller differs:
    - **Anemic (default)** — `IXxxRepository` *and* `IXxxReadRepository` both live in `Application/Interfaces/` (or `Application/Modules/{Module}/Repositories/` when modularized). Business logic sits in handlers and Domain Services never inject repositories, so the only caller of the write-side repository is an Application-layer handler; putting the interface in `Domain` would make `Domain` declare an abstraction it never uses and absorb a persistence concept to do it. `IUnitOfWork`, `IDomainEventDispatcher`, and `IDomainEventHandler<TEvent>` move to `Application` alongside them, so one project owns the whole persistence/dispatch abstraction set and there is no per-interface judgement call. `Domain` stays pure data — entities, value objects, events, enums — which is what makes the zero-package-reference rule easy to hold.
    - **Rich** — `IXxxRepository` lives in `Domain/Interfaces/`, because in DDD the repository is the aggregate's own persistence contract (Evans / eShopOnContainers Ordering); `IUnitOfWork` and the domain-event interfaces stay in `Domain` for the same reason (aggregates queue events, the unit of work dispatches them). `IXxxReadRepository` still lives in `Application/Interfaces/` — it returns DTOs, which `Domain` must not know about.
    - Record which layout is in force in the project README, and do not mix the two.
  - **Repository Abstraction**: Each aggregate gets its own named interface (`IOrderRepository`, `ICustomerRepository`), placed per the rule above, declaring only the operations that aggregate's callers actually use, with no shared base interface. Repositories operate at the aggregate boundary — never expose `IQueryable<T>` outside `Persistence`, never return DTOs, and never call `SaveChanges` (the commit boundary is `IUnitOfWork`). Avoid `GetAllAsync` unless the table is genuinely bounded reference data. Domain Services under either model never inject repositories.
  - **Read Repository Abstraction**: `IXxxReadRepository` is defined in `Application/Interfaces/` and implemented in `Persistence/ReadRepositories/`. It serves QueryHandlers only, returns DTOs/projections rather than aggregates, and never exposes `IQueryable<T>`. It does **not** perform writes and is never injected into a CommandHandler or a Domain Service — a CommandHandler that needs to read does so through the write-side repository, since its reads must come from the write connection and must be tracked. Conversely, QueryHandlers do not inject a write-side `IXxxRepository`: loading a whole aggregate to render a screen over-fetches and drags in navigation properties the view does not need.
    - **Anemic model**: this boundary matters more, not less. Without aggregate roots there is nothing to naturally limit how many repositories a CommandHandler touches, so a write-path component reading four tables is routine. Every one of those reads goes through the **write-side** repository, so they are tracked and come from the write connection. Under the Anemic layout both interfaces sit in `Application`, so project boundaries cannot enforce the separation — a CommandHandler injecting an `IXxxReadRepository` is a defect even though it compiles.
    - **No tooling enforces this boundary under the Anemic layout** — it is upheld by review and the `I*ReadRepository` naming convention (write-side interfaces are every other `I*Repository`).
- 🌐 **Timezone & Time Abstraction**: 📢 **[MANDATORY]** Before running DB migrations or designing schemas, explicitly ask the user for the targeted database timezone. Any expiration/time logic must use **`TimeProvider`** instead of direct system clock calls.

## 🔌 Environment Isolation & Test Backdoors
- 🔌 **Service Toggle**: External services (Email, Storage, Queues) must be interface-driven. In Dev/Test envs, they must default to `LocalFileStorage`, `MockEmailSender` (logs only), or In-Memory Queues.
- 🔐 **OTP & Auth Bypass**: Dev/Test environments may support a `FixedOTP` config (e.g., "123456") and a testing header (e.g., `X-Test-User-Id`) when automated tests need to bypass interactive authentication. These backdoors must be disabled in production.

## ⚙️ Environment & Architecture
- 💻 **SDK**: Implement using **.NET 10**. Solutions must use the modern `*.slnx` format. Central Package Management (CPM) via `Directory.Build.props` and `Directory.Packages.props` is mandatory.
- 📦 **Package Versions**: Always use the **latest stable** version available at scaffold time. Never rely on version numbers stored in this document or from memory — look up the current release on NuGet.org before adding any package. Preview, beta, and RC releases are strictly forbidden.
- 📜 **Package Licensing**: Only **MIT- or Apache-2.0-licensed** packages are permitted. GPL/copyleft-licensed packages are forbidden — they impose obligations incompatible with typical closed-source backends.
- 🔐 **Secrets**: Never hardcode secrets (connection strings, API keys, tokens). Use environment variables or a secret manager for every secret. `.gitignore` must exclude local env files, secrets, and build output.
- 🎨 **Code Style Consistency**: All code across the entire solution **must** adhere to a single, unified code style standard. Establish an `.editorconfig` file at the solution root that enforces naming conventions (PascalCase for public members, camelCase for parameters/locals), indentation (4 spaces), line length limits, and brace placement. Run `dotnet format` as part of the CI/CD pipeline to enforce consistency. No inconsistent naming patterns, formatting, or structural conventions are permitted across projects or layers.
- ✒️ **Constructors**: All classes requiring DI **must strictly use .NET 10 Primary Constructors**. Explicit boilerplate constructor blocks and manual `private readonly` backing fields are prohibited.
- 🌐 **Web Framework**: Use Minimal APIs. Upon endpoint creation, explicitly ask the user if they want to integrate `FastEndpoints` and provide a concise architectural comparison (Route Groups vs FastEndpoints).
- 💾 **Data Access**: Default to **EF Core + Dapper/raw SQL** in the `Persistence` project, but keep `Domain` and `Application` persistence-agnostic. EF Core is the default for aggregate persistence and transactional commands; **Dapper/raw SQL** handles complex/reporting queries and narrowly scoped performance-sensitive updates. The DB provider is decided at project setup — **default to SQL Server, then PostgreSQL**; do not use SQLite. Ask the user before scaffolding.
  - **GUID/UUID Strategy**: When using GUID as primary key or unique identifier in database tables, **MUST always use UUID V7**. UUID V7 provides sequential ordering by timestamp, improving database index performance and query efficiency compared to V4 random GUIDs. Configure EF Core to generate UUID V7 values via `ValueGeneratedOnAdd()` with the appropriate `HasDefaultValueSql()` for the target database (e.g., a UUID V7 wrapper on SQL Server; `gen_random_uuid()` for PostgreSQL with the pgcrypto extension). Note SQL Server's built-in `NEWID()` is random, not V7, and `NEWSEQUENTIALID()` is not time-ordered the same way — prefer generating V7 in application code or a dedicated SQL function when the provider lacks native V7.
  - **Raw SQL update policy**: Repositories may use raw SQL/Dapper `UPDATE` only as a Persistence-layer optimization for batch updates, performance-sensitive narrow updates, counters, flags, or state changes that do not bypass aggregate invariants and do not require domain events. Do not use raw SQL to silently perform core business transitions such as order cancellation, payment completion, inventory deduction, or any operation that requires a domain method, invariant enforcement, or domain event. If a bulk operation requires auditing, explicitly write audit records in the same transaction or load aggregates and invoke domain behavior.
  - **Unit of Work** — `IUnitOfWork` is defined in `Domain/Interfaces/` (Rich) or `Application/Interfaces/` (Anemic; `Application/Common/` in the module-grouped layout) and implemented in `Persistence/UnitOfWork/`. It is a persistence-agnostic transaction/commit boundary with `Task CommitAsync(CancellationToken)`, used by both Rich and Anemic models. It owns **`WriteDbContext` only**. Application command handlers decide when to commit. Repositories must never call `DbContext.SaveChangesAsync()`, commit SQL transactions, or expose EF/SQL transaction types to `Domain` or `Application`.
    - **Rich Domain Model**: `CommitAsync()` persists aggregate changes, commits the transaction, then dispatches collected domain events via `IDomainEventDispatcher` only after the persistence commit succeeds. Clear domain event queues after successful dispatch.
    - **Anemic Domain Model**: `CommitAsync()` commits all repository operations for the use case. Only handlers call it; Domain Services never open transactions or commit.
    - **EF + Dapper/raw SQL**: when both are used in one command, they must share the same connection and transaction owned by `IUnitOfWork`/Persistence. For EF-backed implementations, Dapper/raw SQL repositories in `Persistence` may inject the concrete `AppUnitOfWork` to call `EnsureTransactionAsync()` and use its exposed `Connection` / `CurrentTransaction`. `AppUnitOfWork` must not be exposed to `Domain` or `Application`, and repositories must not create their own independent transactions. Enrolment requires **all three** of: (1) `await EnsureTransactionAsync()` *before* the command — otherwise `CurrentTransaction` is `null`, and a null transaction makes Dapper autocommit the statement as its own independent write (no error, silent consistency break); (2) executing on `AppUnitOfWork.Connection` (EF's own connection), never a freshly constructed one; (3) passing `transaction: AppUnitOfWork.CurrentTransaction`. Passing `CurrentTransaction` while executing on a *different* connection throws (transaction not associated with the connection) or splits the work across two independent transactions. `Connection` and `CurrentTransaction` must both derive from the same `DbContext`.
    - **DI registration**: register `AppUnitOfWork` once per scope, then map `IUnitOfWork` to that same scoped instance. Do not create Persistence-local interfaces solely to access the current transaction.
    - **Open a transaction only when one is needed**: `SaveChangesAsync()` is already atomic, so a use case whose only writer is EF must not open an explicit transaction — `CommitAsync()` simply calls `SaveChangesAsync()`. An explicit transaction exists only once a Dapper/raw-SQL repository has called `EnsureTransactionAsync()`, and `CommitAsync()` branches on whether one is open. After committing **or** rolling back, dispose the transaction and reset the field to `null`: a completed transaction cannot be reused, and leaving it set makes a later `EnsureTransactionAsync()` hand back a dead one, throwing *"This transaction has completed; it is no longer usable"* — a batch job running several use cases inside one scope hits this immediately. Wrap the rollback in its own `try`/`catch` and swallow **its** exception: rolling back can fail on a dropped connection or a server-aborted transaction, and letting that exception propagate masks the original failure the caller actually needs to see. `DisposeAsync()` must roll back explicitly if a transaction is still live — disposal rolls back implicitly, but the intent belongs in the code.
    - **Domain event dispatch happens after the data is already durable.** Under the **Rich** model `CommitAsync()` dispatches internally, so a throwing handler makes `CommitAsync()` itself throw; under **Anemic** the handler calls `DispatchAsync()` after `CommitAsync()` has returned, so the exception surfaces from that call instead. Either way the caller sees a failure even though the write succeeded — the side effect is lost, not the data. This is the reason in-process handlers must stay trivial and non-critical; anything that must happen belongs in retryable background work or an integration event via the outbox. Do not swallow handler exceptions to paper over this — that hides real bugs.
    - **Transaction mechanism**: implement the commit boundary with EF Core's own transaction API — `dbContext.Database.BeginTransactionAsync()` / `IDbContextTransaction` (as the template's `EnsureTransactionAsync()` shows). The `IUnitOfWork` boundary — one connection and one `IDbContextTransaction`, shared by EF and any raw-SQL/Dapper repository — guarantees a single all-or-nothing commit.
  - Calling `DbContext.SaveChangesAsync()`, committing a `DbTransaction`, or directly managing transaction scope from any handler is strictly forbidden regardless of domain model style.
- 🔄 **CQRS Implementation**: Replicate the boilerplate from `references/dotnet-cqrs-template.cs` (same directory as this file) verbatim into **`<ProjectName>.Application/Cqrs/CQRS.cs`** (namespace `<ProjectName>.Application.Cqrs`) — a single file inside the Application project, **not** a standalone `Cqrs` project. It contains **only** the core infrastructure (interfaces, dispatchers, `AddCqrs` extension) — no business commands, queries, or handlers. All command/query/handler implementations live elsewhere in the same `Application` project (`Commands/`, `Queries/`, `EventHandlers/`). Manual, line-by-line registration of handlers is prohibited; you must invoke `services.AddCqrs(typeof(SomeHandler).Assembly)` in `Api`.
  - **Database topology is fixed and never a user choice** — CQRS **and** the read/write split are mandatory in every scaffolded project. There is always a `WriteDbContext` bound to `ConnectionStrings:Write` and a `ReadDbContext` bound to `ConnectionStrings:Read`; there is no `ConnectionStrings:Default` and no single-context shape. When no replica is provisioned (local development, small deployments) both keys hold the **same value** — the split is then logical rather than physical, and adding a real replica is a config change only. The routing rules below are always binding.
  - **Write vs Read routing** — the default is mechanical: **Command ⇒ Write, Query ⇒ Read**. Overrides are a closed list, not a judgement call:
    - **CommandHandlers always use Write — no exceptions.** This includes every read a command performs: validation, invariant checks, idempotency checks, aggregate loading, uniqueness checks, and read-before-write logic. Replication lag on any of these silently breaks business invariants.
    - **QueryHandlers use Read by default** — list/search/paging, reports and aggregates, master-data lookups (dropdowns), audit-trail browsing. Simple queries use EF Core + LINQ with `AsNoTracking()`; complex, reporting, or multi-join queries use Dapper/raw SQL. Both go to Read.
    - **QueryHandlers must use Write in these cases only**: (1) the query backs a page the user is redirected to immediately after a command that changed it (read-your-writes); (2) the query is a later step in one user-visible operation sequence whose earlier step wrote; (3) the value must be exact at read time — balance, stock, quota, credit limit; (4) the query decides uniqueness or existence in order to permit a subsequent write; (5) the query reads current state-machine status or distributed-lock state.
    - Anything not on that list goes to Read. "It feels safer on Write" is not a reason — routing ordinary query load to the master defeats the split entirely.
  - **How to route a query to Write**: handlers cannot inject a `DbContext` — `Application` references `Domain` only — so the mechanism lives in `Persistence`. Register a second implementation of the same `IXxxReadRepository` bound to the write context and resolve it with a keyed service (see `dotnet-scaffold.md` → CQRS Pattern); the handler still depends only on the Application-layer read interface. State the reason in a comment on the handler naming which of the five cases above applies. Never make Write the ambient default for a shared read abstraction.
  - **Persistence abstractions**: `IXxxRepository` (write side, returns aggregates/entities) and `IXxxReadRepository` (read side, `Application/Interfaces/`, returns DTOs) always both exist and are both implemented in `Persistence`; `IXxxRepository` is placed per *Where repository interfaces live*. Whether a replica physically exists changes `appsettings` only — never a handler, an interface, or a query body.
  - **DbContext separation**: `DbContext` types stay inside `Persistence` and are never injected into `Application`. `WriteDbContext` (on `ConnectionStrings:Write`) and `ReadDbContext` (on `ConnectionStrings:Read`) both derive from a shared abstract `AppDbContext` so the model is configured once. Write repositories and `IUnitOfWork` take `WriteDbContext`; read-repository implementations take `ReadDbContext`. `ReadDbContext` is `NoTracking` by default and its `SaveChanges` throws. Dapper/raw SQL read queries use `ReadDbContext`'s connection; Dapper/raw SQL writes use `AppUnitOfWork.Connection` (Write). EF Core migrations and the design-time factory bind to the **Write** connection only. A transaction never spans both contexts. Do not register a single `AppDbContext` in DI, and do not add `DbSet`s or `OnModelCreating` overrides to `ReadDbContext`.
- 📡 **Event-Driven Design (EDD)** (decided at project setup — ask the user):
  - **Domain Events** (in-process) — raised inside aggregates, dispatched synchronously via `IDomainEventDispatcher` after `IUnitOfWork.CommitAsync()` commits persistence successfully. For decoupling non-critical in-process side effects within a single service boundary. Never dispatch before the transaction commits. In-process domain event handlers must not perform irreversible or reliability-critical side effects directly.
  - **Integration Events** (cross-service) — optional. Enable only when the project has confirmed cross-service asynchronous communication. Events are defined in `Application/IntegrationEvents/`. `IEventBus` interface lives in `Application/Interfaces/`; the broker-specific implementation lives in `Infrastructure/`.
  - Email, external API calls, cross-service notifications, and durable projections must not be performed directly in in-process domain event handlers. Prefer explicit Application orchestration for simple workflows; use retryable background work with idempotency when asynchronous processing is required.
  - Integration event consumers must be **idempotent** — processing the same event twice must produce the same outcome.
- 🪵 **Logging**: Standardize exclusively on **Serilog** — mandatory in every project; never ask whether to install it. All log calls **must** use structured message templates with named placeholders — string interpolation in log messages is strictly prohibited.
  ```csharp
  // ❌ Forbidden — string interpolation destroys structure
  logger.LogInformation($"User {userId} purchased {productId} for {amount}");

  // ✅ Required — structured template with named properties
  logger.LogInformation("User {UserId} purchased {ProductId} for {Amount}", userId, productId, amount);
  // 'logger' is the Primary Constructor parameter — no _logger backing field
  ```
  - **Bootstrap logger**: `Program.cs` must configure a bootstrap `Log.Logger` before `WebApplication.CreateBuilder()` to capture startup errors. Wrap the entire host startup in `try/catch/finally` with `Log.CloseAndFlush()` in the `finally` block.
  - **Request logging**: Always call `app.UseSerilogRequestLogging(...)` with a custom `MessageTemplate` that includes `{RequestMethod}`, `{RequestPath}`, `{StatusCode}`, and `{Elapsed}`. This replaces the verbose default ASP.NET Core request logging with a single structured entry per request.
  - **Enrichers** (mandatory, add to Api project): `Serilog.Enrichers.Environment` (`WithMachineName`), `Serilog.Enrichers.Process` (`WithProcessId`), `Serilog.Enrichers.Thread` (`WithThreadId`). Register them only in the `appsettings.json` `"Enrich"` array (`FromLogContext`, `WithMachineName`, `WithProcessId`, `WithThreadId`) — never also via `.Enrich.WithXxx()` in `Program.cs`.
  - **Configuration**: Serilog must be fully configured via `appsettings.json` using `ReadFrom.Configuration()`. Hard-coded sink configuration in `Program.cs` is forbidden. Use `ReadFrom.Services()` to allow DI-resolved sinks.
  - **Sinks**:
    - **File** is mandatory under `--otel none`. Under `--otel otlp` it ships too, but may be disabled by commenting out or deleting its `WriteTo` entry — the .NET JSON configuration provider accepts `//` and `/* */` comments. Delete instead of commenting when a strict JSON tool (`jq`, a CI/CD config-substitution step) processes the file.
    - **Console** is mandatory in Development: `appsettings.Development.json` declares its own `WriteTo:Console`, so editing the base file never removes it.
    - **`WriteTo` is a named-key object, never an array.** Environment files and environment variables merge by key (`Serilog__WriteTo__File__Args__path`), not by array index, and adding a sink is adding a key.
    - In production, point the File `path` at persistent storage through `Serilog__WriteTo__File__Args__path` — a container's local disk is lost on restart, and each instance writes its own file.
  - **Trace correlation**: Every sink `outputTemplate` must include `{TraceId}` and `{SpanId}`. Serilog captures them from `Activity.Current` (W3C trace context), so each log line can be matched to its trace — the OpenTelemetry trace when OTel is enabled.
  - **Log levels**: Production default is `Information`; override `Microsoft.*` and `System.*` to `Warning`; Development overrides to `Debug`. EF Core SQL commands: `Microsoft.EntityFrameworkCore.Database.Command` → `Information` in Development only.
  - **Sensitive data**: Never log passwords, tokens, PII, or connection strings. Destructure objects explicitly; do not log entire request/response bodies unless redacted.
- 📊 **Tracing & Metrics**: Mandatory in every project, with or without OpenTelemetry — never ask whether to include them. Both use the built-in .NET APIs (`System.Diagnostics.Activity` / `ActivitySource`, `System.Diagnostics.Metrics.Meter`); no package is needed.
  - **Naming**: every custom `ActivitySource` and `Meter` name starts with `<ProjectName>.` (e.g. `Acme.OrderService.OrderSync`). The `none` listener and the OTel `AddSource`/`AddMeter("<ProjectName>.*")` registrations both rely on this prefix, so a new source or meter needs no `Program.cs` change.
  - **Tracing**: ASP.NET Core starts an `Activity` per HTTP request and propagates it downstream through the W3C `traceparent` header. Under `--otel none` traces are used for log correlation only (no trace view) — `Program.cs` registers an `ActivityListener` for the `<ProjectName>.` sources so `StartActivity()` returns an activity instead of `null`.
  - **Metrics**: ASP.NET Core, Kestrel, HttpClient and the runtime publish meters out of the box. Create custom meters through the injected `IMeterFactory`, never `new Meter(...)`. Under `--otel none` they are observed with `dotnet-counters` / `dotnet-monitor`.
  - **Background work must start its own `Activity`**: `BackgroundService`, scheduled jobs, and message consumers get no request `Activity`, so their logs carry an empty `TraceId`. Start one `Activity` per unit of work (one loop iteration, one message) from an `ActivitySource` named under the `<ProjectName>.` prefix.
  ```csharp
  internal sealed class OrderSyncWorker(ILogger<OrderSyncWorker> logger) : BackgroundService
  {
      public const string ActivitySourceName = "Acme.OrderService.OrderSync";
      private static readonly ActivitySource Source = new(ActivitySourceName);

      protected override async Task ExecuteAsync(CancellationToken ct)
      {
          while (!ct.IsCancellationRequested)
          {
              using (Source.StartActivity("OrderSync.Run"))
              {
                  logger.LogInformation("Order sync started"); // carries this run's TraceId
                  // ... one unit of work ...
              }
              await Task.Delay(TimeSpan.FromMinutes(1), ct);
          }
      }
  }
  ```
- 🔭 **OpenTelemetry (optional, `--otel otlp`)**: Defaults to none — `--otel none` installs no OTel package. Enable it only when the project ships telemetry to an observability backend.
  - Install `OpenTelemetry.Extensions.Hosting`, `OpenTelemetry.Instrumentation.AspNetCore`, `OpenTelemetry.Instrumentation.Http`, `OpenTelemetry.Exporter.OpenTelemetryProtocol` in the `Api` project.
  - OTLP is the only exporter: logs, traces and metrics all leave through `UseOtlpExporter()`. Serilog stays the only logging entry point — `writeToProviders: true` forwards its events to the OTel logger provider, and `ClearProviders()` stops the default Console provider from printing every line twice. Console and File remain Serilog sinks.
  - Remove the `none`-mode `ActivityListener` when OTel is added: sampling takes the most permissive listener, so it would override the OTel sampler.
  - Register in `Program.cs`:
  ```csharp
  builder.Logging.ClearProviders();
  builder.Host.UseSerilog((ctx, services, lc) => lc
      .ReadFrom.Configuration(ctx.Configuration)
      .ReadFrom.Services(services),
      writeToProviders: true);

  builder.Services.AddOpenTelemetry()
      .ConfigureResource(resource => resource.AddService(builder.Environment.ApplicationName))
      .WithTracing(tracing => tracing
          .AddSource("<ProjectName>.*")
          .AddAspNetCoreInstrumentation()
          .AddHttpClientInstrumentation())
      .WithMetrics(metrics => metrics
          .AddMeter("<ProjectName>.*")
          .AddAspNetCoreInstrumentation()
          .AddHttpClientInstrumentation())
      .WithLogging()
      .UseOtlpExporter();
  ```
- 🔌 **Connecting an external backend**: Business code only ever uses `ILogger<T>`, `ActivitySource` and `Meter`; switching backends changes configuration, never business code. Two outlets, usable together:

  | Outlet | How to add a destination | Carries |
  |---|---|---|
  | Serilog sink | Add the sink package, then a named key under `appsettings.json` `WriteTo` | Logs |
  | OTLP (`--otel otlp`) | `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_HEADERS`, `OTEL_EXPORTER_OTLP_PROTOCOL` environment variables; backends without native OTLP intake go through an OpenTelemetry Collector | Logs, traces, metrics |

  - A sink must be maintained by the vendor or the Serilog organization, and licensed MIT or Apache 2.0.
  - Example — ELK: OTLP to Elastic's OTLP intake, `Elastic.Serilog.Sinks` straight to Elasticsearch, or File/Console collected by Filebeat/Logstash.
- 🔗 **HTTP Client & Resilience**: Any outbound HTTP call to an external Web API **must** use a named/typed `HttpClient` registered via `AddHttpClient(...)` with **`Microsoft.Extensions.Http.Resilience`**. Call `.AddStandardResilienceHandler()` on every registration — this enables the built-in defense pipeline: Rate Limiting → Timeout → Retry → Circuit Breaker. Raw `HttpClient` instantiation (`new HttpClient()`) is strictly prohibited.
  ```csharp
  services.AddHttpClient("PaymentClient", c => c.BaseAddress = new Uri(config["Payment:BaseUrl"]!))
      .AddStandardResilienceHandler(options =>
      {
          options.Retry.MaxRetryAttempts = 3;
          options.CircuitBreaker.FailureRatio = 0.5;
      });
  ```
- 📡 **API Documentation**: Use `Microsoft.AspNetCore.OpenApi` (`AddOpenApi()`) with **Scalar** (`Scalar.AspNetCore`) for API documentation UI. Do NOT use Swashbuckle or Swagger UI under any circumstance.
- 📋 **Validation**: Use **FluentValidation** for all request/command/query validation. Validators live in `Application/Validators/`. Package split: `FluentValidation` is referenced by the `Application` project; `FluentValidation.DependencyInjectionExtensions` is referenced by `Api` and registered via `AddValidatorsFromAssembly(typeof(SomeValidator).Assembly)`. At the endpoint layer, invoke validation using `await validator.ValidateAndThrowAsync(request, ct)` before dispatching commands/queries. Never use DataAnnotations for business rule validation — DataAnnotations are permitted only for OpenAPI metadata hints.
- 🗃️ **Caching**: Do not scaffold caching by default. If the project has a confirmed caching need, prefer **`HybridCache`** and avoid direct `IDistributedCache` / `IMemoryCache` usage in application code. `HybridCache` requires the **`Microsoft.Extensions.Caching.Hybrid`** package (it is *not* built into the shared framework) — add it and call `builder.Services.AddHybridCache()` only when caching is actually needed.
- 🗺️ **Object Mapping**: **AutoMapper is strictly prohibited — no exceptions.** Always use **Mapperly** (`Riok.Mapperly`) — fixed in every project; never ask, never offer an alternative. Source generator; zero runtime overhead, compile-time type safety. Mapper classes live in `Application/Mappers/`. Add to `Application.csproj` with `<PrivateAssets>all</PrivateAssets>` to prevent the analyzer from leaking as a transitive runtime dependency.

## 🧪 Testing Guidelines
- 🧪 **Required Test Projects**: Every scaffolded solution must include exactly these baseline test projects:
  - `tests/<ProjectName>.UnitTests/` for isolated unit tests of domain logic, validators, mappers, and application handlers.
  - `tests/<ProjectName>.IntegrationTests/` for ASP.NET Core request pipeline, DI, persistence, and infrastructure integration tests.
- 🧪 **Unit Tests**: Use **xUnit** as the test framework and **NSubstitute** for mocks. Assert with xUnit's built-in `Assert`. Unit tests must not use real DB, filesystem, network, or external services. Outbound HTTP calls must be stubbed or intercepted.
- 🧪 **Integration Tests**: Use **Microsoft.AspNetCore.Mvc.Testing** / `WebApplicationFactory` with a test web host. The integration test project must use the Web SDK. Integration tests must cover representative request/response flows, DI wiring, validation behavior, persistence behavior, and error responses.
- 🧪 **Coverage Standard**: Placeholder tests are not sufficient. Every generated or implemented feature must include meaningful unit and/or integration tests that verify expected behavior, failure paths, and important boundary conditions. The scaffold is not complete until `dotnet test` passes with these meaningful tests.
- 🧪 **Excluded Test Projects**: Do not scaffold any test project other than `UnitTests` and `IntegrationTests` as part of this skill. If a future project needs more test projects, treat them as a separate explicit request outside the default backend scaffold.
