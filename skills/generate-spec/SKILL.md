# 產出 Spec（功能規格）

Spec 定義**使用者需要什麼、為什麼需要**，並且要寫到能直接當驗收依據。它是 Plan 與 Tasks 的唯一輸入。

採 **GitHub Spec Kit** 的規格格式。

> **語言**：與使用者的對話使用正體中文，Spec 內容亦以正體中文撰寫。以下保留英文原文：RFC 2119 關鍵字（MUST / SHALL / SHOULD / MAY）、Given / When / Then、`FR-` `SC-` `US` 等編號前綴、`[NEEDS CLARIFICATION]` 標記、技術識別名詞（欄位名、狀態值）。

## 核心原則

```
✅ 專注於使用者需要什麼（WHAT）以及為什麼（WHY）
❌ 避免寫如何實作（HOW）——不寫技術選型、API 設計、程式結構
```

這條界線讓 Spec 在換掉實作技術時仍然成立。判準：**實作可以改變而對外可觀察行為不變的，就不屬於 Spec。**

**例外**：對外 API 路由、request / response 欄位、錯誤碼屬於對外契約，前端與測試依賴它們，可以寫進 Spec。

## 不要臆測：使用 [NEEDS CLARIFICATION]

這是 Spec Kit 最重要的機制，也是這個技能最容易被忽略的部分。

需求沒講清楚時，**不要挑一個看起來合理的解釋往下寫**。LLM 天生傾向填補空白——把「登入功能」自動想成帳號密碼登入——但猜錯的成本是整份 Spec 連同後續 Plan 與實作都建立在錯誤前提上。

作法是照樣把 Spec 寫完整，但在不確定處留下標記：

```markdown
- **FR-006**: 系統 MUST 於案例送審後產生案例編號 [NEEDS CLARIFICATION: 退回重送時是否沿用原編號？]
- **FR-007**: 系統 MUST 保留已下架案例 [NEEDS CLARIFICATION: 保留期限未定義]
```

標記格式是 `[NEEDS CLARIFICATION: 具體的問題]`——要寫出**問題本身**，不是只標「待確認」，這樣使用者才能直接回答。

這個作法比「需求沒確認就不建檔」好，因為它讓骨架先成形、把不確定處集中暴露出來，而不是整份卡住。但相對地，**Spec 交付審查時若仍有標記殘留，就不算通過**——見文末檢查清單。

## 審視 SRS：把風險與疑慮提出來

SRS 是 SA 交付的輸入，但**「已交付」不等於「沒問題」**。寫 Spec 的過程是這份需求第一次被逐條推敲，你會看到 SA 在撰寫時未必看得到的東西。看到了就要說。

這跟 `[NEEDS CLARIFICATION]` 是兩件事：

| | `[NEEDS CLARIFICATION]` | 風險與疑慮 |
| :--- | :--- | :--- |
| 針對 | 需求**沒寫到**的空白 | 需求**寫了，但可能有問題** |
| 例子 | 「保留期限未定義」 | 「保留期限設 10 年，但個資法要求目的達成後應刪除」 |
| 標記位置 | 就地標在該條 FR 後面 | 集中寫在「風險與疑慮」段落 |
| 阻擋交付嗎 | 是，標記未清不得進 Plan | 否，但必須在交付時明確提出 |

### 要主動檢查的方向

逐條讀 SRS 時，針對每項需求問自己：

- **前後矛盾** — 這條跟前面哪一條打架？同一個概念在不同段落是不是有兩種定義？
- **與現況衝突** — 這條跟對話中已知的既有行為或資料是否牴觸？只根據你已確知的事實判斷，不要另行假設。
- **法規與個資** — 涉及個人資料、保存期限、稽核軌跡、跨境傳輸時，需求的作法站得住腳嗎？
- **資安** — 權限邊界講清楚了嗎？誰能看到什麼？有沒有「所有人都能下載全部資料」這類未設限的操作？
- **可行性與規模** — 需求隱含的資料量、併發量、回應時間，用現有架構做得到嗎？例如「一鍵下載全部案例與附件」在資料量成長後會不會拖垮伺服器？
- **對外依賴** — 依賴的外部系統真的支援這個需求嗎？無法確認時標記 `[NEEDS CLARIFICATION]`，不要假設。
- **遺漏的反面情境** — 需求只寫了成功路徑嗎？失敗、逾時、併發衝突、權限不足時該怎樣？

### 寫法

在 Spec 末尾加一段（沒有風險時整段省略，不要寫「無」充數）：

```markdown
## 風險與疑慮

- **[風險] 一鍵下載無筆數上限**
  SRS 3.2 要求匯出全部案例與附件，但未設上限。以目前資料量估算單次匯出可能超過數 GB，
  會長時間佔用連線與磁碟。
  **建議**：設定筆數門檻，超過改為非同步產製後通知下載。
  **需要決定**：門檻訂在多少？

- **[矛盾] 草稿可見範圍前後不一致**
  SRS 2.1 寫「草稿僅建立者可見」，4.3 的畫面說明卻列出管理者可瀏覽所有草稿。
  **建議**：以 4.3 為準（管理者可見），因為它與現行實作一致。
  **需要決定**：請 SA 確認。
```

每則包含四個要素：**類型標籤**（`[風險]` / `[矛盾]` / `[法規]` / `[資安]` / `[可行性]`）、**具體事實**（指出是 SRS 哪一節，不要泛泛而談）、**建議作法**、**需要誰決定什麼**。

### 分寸

- **提出，不要自行改需求。** 你的角色是讓問題浮上檯面讓人決定，不是替 SA 重寫需求。
- **要具體。** 「可能有效能問題」沒有價值；「單次匯出估計超過數 GB」才能讓人判斷。
- **不確定就說不確定。** 沒把握是不是真問題時，照樣提出並註明你的把握程度，不要因為怕說錯而吞下去。
- **不要為了湊數而寫。** 沒有風險就不寫這段。虛構的疑慮會稀釋真正重要的那幾條。

## 文件結構

依序包含下列段落。標示 *(必要)* 的不可省略。

```markdown
**建立日期**：[YYYY-MM-DD]
**狀態**：Draft
**來源**：[SRS 版本 / 工作項目編號 / 設計稿節點]

## 修訂紀錄

[用平白的話描述這段使用者旅程]

**為何是此優先序**：[說明價值，以及為什麼排在這個位置]

**獨立測試方式**：[如何單獨驗證這個故事——例如「可透過建立一筆草稿案例並以一般使用者身分查詢來完整驗證」]

- **[實體名]**: [代表什麼、關鍵屬性，不寫實作型別]

## 成功標準 *(必要)*

- **SC-002**: [可量測的指標]

  [具體事實，指出 SRS 哪一節]
  **建議**：[你的建議作法]
  **需要決定**：[需要誰決定什麼]
```

## 各段落的寫法

### User Story 必須可獨立驗證

這是 Spec 與 SRS 最關鍵的差別，值得特別說明。

SRS 的 User Story 通常寫到「作為管理者，我想要新增案例，以便擴充知識庫」就結束了。Spec 的 User Story 必須再往前兩步：**獨立測試方式**與**驗收情境**。

要求每個故事可獨立驗證，是為了讓它能單獨開發、單獨測試、單獨交付——只實作 P1 也應該是一個能用的最小可行版本。這個約束會逼你把故事切在對的地方：切得太細會發現無法獨立交付，切得太粗會發現測不完。

優先序 P1 / P2 / P3 依價值排序，P1 最關鍵。

### 功能需求要可測試

每條 FR 用 `FR-XXX` 編號，供 Plan 與 Tasks 回頭對照。編號一旦發出就不要重排，需求作廢就標記作廢而非回收號碼——否則跨文件的追溯會斷掉。

寫法上，功能導向的句子（「系統提供查詢功能」）無法驗證，因為它沒說結果該是什麼。改成行為導向：

| 不可驗證 | 可驗證 |
| :--- | :--- |
| 系統提供草稿功能 | 系統 MUST 將草稿狀態的案例排除於一般使用者的查詢結果之外 |
| 支援樂觀鎖 | 更新請求挾帶的 rowVersion 與現況不符時，系統 MUST 拒絕更新並回報衝突 |
| 案例可分類 | 每筆案例 MUST 關聯至恰好一個樣態；未指定時系統 MUST 拒絕建立 |

RFC 2119 強度：**MUST / SHALL** 為絕對要求，不符合即缺陷；**SHOULD** 為建議，允許有正當理由的例外；**MAY** 為選用。多數業務需求用 MUST。

### 成功標準必須可量測且不綁技術

`SC-XXX` 描述「怎樣算做成功了」，且必須避開技術用語——它要能讓不懂實作的人驗收。

| 不合格 | 合格 |
| :--- | :--- |
| 查詢效能good | 一般使用者查詢案例列表，95% 的請求在 2 秒內回應 |
| 使用 Redis 快取避免重複下載 | 相同條件的重複匯出請求，5 分鐘內不重複產製檔案 |
| 索引同步正常 | 案例發布後 1 分鐘內可透過全文檢索找到 |

注意第二列：「使用 Redis」是 HOW，屬於 Plan；「5 分鐘內不重複產製」是可量測的對外行為，屬於 Spec。

### 主要實體只寫概念

涉及資料的功能才需要這段。寫實體代表什麼、有哪些關鍵屬性、彼此什麼關係——但**不寫型別、不寫資料表、不寫主鍵策略**，那些是 Plan 的 data model。

### 邊界情況與假設

邊界情況涵蓋業務上結果不同的分支：權限不足、狀態不符、資料不存在、並行衝突。不必窮舉錯誤碼。

假設段落記錄你在需求未明時採用的預設。與 `[NEEDS CLARIFICATION]` 的分別是：**影響大、猜錯會白做的用標記**（必須得到答覆）；**影響小、有合理預設的寫進假設**（審查時順帶確認即可）。

## 切分粒度

一個功能一份 Spec，以「一個使用者能完成的完整任務」為單位。

```
docs/specs/
├── 訂單管理/
│   ├── 訂單建立.md
│   └── 訂單查詢.md
└── 會員/
    └── 會員註冊.md
```

主題只有單一功能時直接放主題層，不必為了對稱硬開子目錄。

## 交付前自我檢查

寫完後逐項確認，這份清單等同 Spec 的單元測試：

**需求完整性**
- [ ] 沒有殘留的 `[NEEDS CLARIFICATION]` 標記（若仍有，須在交付時明確列出待使用者答覆）
- [ ] 每條 FR 都可測試且語意明確
- [ ] 每個 User Story 都有獨立測試方式與至少一條驗收情境
- [ ] 成功標準可量測
- [ ] 邊界情況已涵蓋主要錯誤分支

**SRS 審視**
- [ ] 已逐條讀過 SRS，檢查前後矛盾、與現有實作衝突、法規個資、資安、可行性、外部依賴
- [ ] 發現的風險都寫進「風險與疑慮」段落，且每則都有具體事實與建議
- [ ] 沒有為了湊數而虛構風險

**內容界線**
- [ ] 沒有出現類別、方法、檔案名稱
- [ ] 沒有出現框架或套件選擇
- [ ] 沒有出現資料表結構或欄位型別
- [ ] 成功標準不含技術用語

## 交付

寫入 `docs/specs/` 對應路徑，然後告訴使用者：

- 檔案位置
- 涵蓋幾個 User Story、幾條 FR
- **所有 `[NEEDS CLARIFICATION]` 標記，逐條列出供答覆**
- **所有風險與疑慮，逐條列出**——特別是牴觸法規、資安或現有實作的那幾則。這是整份交付裡最需要人做決定的部分，不要只寫在檔案裡就算數，要在對話中直接講。
- 你在「假設」段落採用的預設

然後**停下來等審查**。這是流程的階段閘門，未經確認不得進入 Plan。不要把沉默當成同意。

## Spec 是系統當前行為的唯一真實來源

這是整個流程的核心約定：**`docs/specs/` 描述系統「現在是什麼行為」，不是「當初打算做什麼」。**

Spec 不是寫完就封存的歷史文件。任何改變對外可觀察行為的事情，最後都必須回到 Spec：

- SRS 交付的新功能
- 只寫在工作項目留言裡的需求變更
- 實作過程中與使用者確認後改變的行為
- 修 bug 時發現「當初講好的就是錯的」而重新議定的規則

只要有人問「這個系統在這個情境下應該怎麼反應」，答案要能在 Spec 裡找到。找不到，就是 Spec 落後了。

**反過來也成立**：Spec 寫的東西如果系統做不到，那不是「文件寫得比較理想」，那是缺陷——不是 Spec 的缺陷就是程式的缺陷，必須有人決定是哪一種。

### 不寫進 Spec 的東西

界線是**對外可觀察行為**：

| 寫進 Spec | 不寫進 Spec |
| :--- | :--- |
| 使用者看得到、測得出來的行為變化 | 修好一個不該發生的崩潰 |
| 新增或修改的驗收條件 | 重構、改名、效能調校（行為不變） |
| 議定後改變的業務規則 | 實作手法、技術選型（那是 Plan） |

修 bug 讓程式「終於做到 Spec 已經寫的事」，Spec 不用動——它本來就是對的。

## 修改既有 Spec

`docs/specs/` 下的檔案與 `docs/` 一樣，修改前須經使用者同意。先說明要改什麼、為什麼改。

已實作功能的 Spec 若與程式碼實際行為不符，先回報落差讓使用者決定——是 Spec 寫錯要修正，還是程式碼有 bug 要修。**不要逕自把 Spec 改成符合現況**，那會把缺陷洗成規格。

修訂時：

- 改動具體的 `FR-###` 與驗收情境，不要整份重寫——編號要能被 Plan 與測試持續對照。
- 已發出的編號不重排，需求作廢就標記作廢而不是回收號碼。
- 在文件的「修訂紀錄」註明日期、來源（工作項目編號 / SRS 版本）、改了什麼。半年後要看得出某條 FR 是原始需求還是後來議定的。

## 不為工程決策製造 Spec

沒有對外業務行為的工作（資料庫遷移策略、外部介接機制、跨切面基礎設施）直接進 Plan。硬套 User Story 與 FR 只是儀式。

## 不要替需求鍍金

Spec 的範圍是 SRS 的範圍。**不要自己加需求。**

寫 Spec 時很容易想「順便加個排序好了」「應該也要能匯出吧」——這些想法可能是對的，但它們沒有經過需求確認、沒有人排優先序、也不在任何人的預期工時裡。多寫進去的每一條 FR 都會變成實作、測試與維護成本。

判準：**每條 FR 都要能追溯到 SRS 的某一段。** 追不到就不該存在。

真的覺得少了什麼，寫進「風險與疑慮」段落提出來（例如「SRS 未提及列表排序，使用者可能預期有此功能」），**讓使用者決定要不要納入**，不要逕自寫成 FR。

同理，也不要為了看起來完整而膨脹 User Story 數量或塞入邊界情況。Spec 越短越好——只要它涵蓋 SRS 要求的全部。
